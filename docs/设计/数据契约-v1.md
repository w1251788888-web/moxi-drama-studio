# 数据契约 v1（S1.4）

> 依据：`docs/adr/001-目标架构.md` §3/§4
> 状态：**定稿候选**（G1 后改动需记决策日志）
> 所有时间字段用 ISO 8601 带时区；所有 id 用 `<前缀>_<26位 ULID>`。

## 1. 目录契约

```
<projectsRoot>/                 # Host Config.projectsRoot，默认 ~/Documents/Moxi/projects
└── <projectId>/
    ├── project.json            # 必需，项目元数据
    ├── canvas.json             # 必需，画布图（唯一可变结构文件）
    ├── content/<nodeId>.md     # 可选，节点正文
    ├── assets/                 # 可选，资产附件
    ├── history/events.jsonl    # 必需，追加式事件流
    ├── versions/<nodeId>/<ver>.md  # 可选，不可变版本快照
    └── exports/                # 可选，导出产物
```

**写入纪律**：
- 所有写操作先写 `<file>.tmp.<rand>` 再 `fs.rename`（原子替换）。
- `canvas.json` 的写入必须持项目级串行锁（同进程内 Map<projectId, Promise>）。
- `history/events.jsonl` 只追加，不重写。
- 删除项目 = 移动到 `<projectsRoot>/.trash/<projectId>.<ts>`，不物理删除。

## 2. project.json（schemaVersion = 1）

```jsonc
{
  "schemaVersion": 1,
  "id": "proj_01JBXYZ...",
  "title": "我的父母没素质",              // trim 后非空；同目录内唯一
  "logline": "",                        // 一句话故事
  "genre": { "main": "家庭", "sub": "" },
  "audience": "女频",                    // 男频 | 女频 | 混合
  "format": "真人短剧",                  // 真人短剧 | 话剧 | 影视剧 | 长剧
  "episodeCount": 60,                   // 用户确认的集数；null = 未确认
  "episodeSeconds": 90,
  "wordRange": { "min": 1000, "max": 1550 },   // 由 episodeSeconds 折算（D-06 公式）
  "sceneHeaderStyle": "bracket",         // bracket | plain
  "status": "active",                   // active | archived
  "rulesPack": "rules/v2",
  "createdAt": "2026-11-06T01:50:00+08:00",
  "updatedAt": "2026-11-06T01:50:00+08:00"
}
```

**校验**（Host 层强制）：
- `title` trim 非空；同一 `projectsRoot` 下不区分大小写唯一 → 冲突返回 `E_DUP_TITLE`。
- `episodeCount` 为 `null` 时禁止生成分集节点（对应旧系统 `episode_count_status`）。
- `wordRange` 若缺失，由 `episodeSeconds × 字数/秒` 公式回填（口径见 D-06）。

## 3. canvas.json（schemaVersion = 1）

```jsonc
{
  "schemaVersion": 1,
  "rev": 12,                            // 每次变更 +1，UI 轮询判断
  "viewport": { "x": 0, "y": 0, "zoom": 1 },
  "nodes": [ /* Node */ ],
  "edges": [ /* Edge */ ]
}
```

### 3.1 Node

```jsonc
{
  "id": "n_01JBXYZ...",
  "type": "project_root",               // 见 §3.2
  "title": "项目根",
  "status": "draft",                    // 见 §4
  "x": 0, "y": 0, "w": 320, "h": 200,
  "ref": { "episode": null, "scene": null },   // 业务引用
  "contentFile": null,                  // 相对项目根；有正文时为 "content/n_xxx.md"
  "contentVersion": 0,                  // 正文版本号（乐观锁）
  "meta": {},                           // §3.2 定义的类型特有字段
  "createdAt": "...", "updatedAt": "..."
}
```

### 3.2 九类节点与 `meta` 字段

| type | 中文 | 内容载体 | meta 关键字段 |
|---|---|---|---|
| `project_root` | 项目根 | 无（读 project.json） | `{ audience, genre, episodeCount, logline }`（镜像展示用） |
| `settings` | 设定集 | `content/<id>.md` | `{ coreFields: {summary, worldview, goldenFinger, coreConflict} }` |
| `asset` | 角色·场景·道具 | `content/<id>.md` | `{ assetKind: "character"\|"scene"\|"prop", fields: {...} }` |
| `beat_sheet` | 分集节拍 | `content/<id>.md` | `{ episode: 1, hooks: [], anchors: [] }` |
| `scene_list` | 分场表 | `content/<id>.md` | `{ episode: 1, scenes: [{no, location, time, summary}] }` |
| `script_scene` | 剧本场次 | `content/<id>.md` | `{ episode: 1, sceneNo: "1-1", wordCount, segment: 1 }` |
| `quality` | 质检 | `content/<id>.md`（报告） | `{ episode: 1, findings: [], rubric: {}, verdict: null }` |
| `compliance` | 合规 | `content/<id>.md`（报告） | `{ episode: 1, findings: [], highestRisk: "none" }` |
| `delivery` | 分镜·成片·导出 | `content/<id>.md`（清单） | `{ format: "docx"\|"txt"\|"md", exportPath: null }` |

### 3.3 Edge

```jsonc
{ "id": "e_01JBXYZ...", "from": "n_a", "to": "n_b", "kind": "dependency" }  // dependency | context
```

约束：禁止自环、禁止重复边（同 from/to/kind）、禁止成环（`dependency` 子图必须 DAG）。

## 4. 状态机

```
draft ──generate──▶ generating ──done──▶ review ──approve──▶ approved
  ▲                    │                    │
  └──────retry─────────┘                    └──reject──▶ rejected ──revise──▶ draft
```

| from | 允许的 to | 触发 |
|---|---|---|
| `draft` | `generating` | 生成开始 |
| `generating` | `review` / `draft` | 生成完成 / 失败回退 |
| `review` | `approved` / `rejected` | 人工或质检判定 |
| `rejected` | `draft` | 返修 |
| `approved` | （终态；改内容需显式 `reopen`） | — |
| 任意（被依赖） | `blocked` | 上游 `rejected`/`blocked` 时系统置位；解除后回退到原状态 |

**错误码**：`E_TRANSITION`（非法迁移，附 `allowed` 列表）、`E_BLOCKED`（上游未批准）。

## 6. Host API DTO（与 ADR-001 §4 对应）

统一响应信封：

```jsonc
{ "ok": true,  "value": {...} }
{ "ok": false, "error": { "code": "E_...", "message": "...", "details": {...} } }
```

错误码表：

| code | HTTP | 含义 |
|---|---|---|
| `E_BAD_REQUEST` | 200（信封） | 入参不合法 |
| `E_NOT_FOUND` | 200 | project/node 不存在 |
| `E_DUP_TITLE` | 200 | 项目名重复 |
| `E_TRANSITION` | 200 | 非法状态迁移 |
| `E_BLOCKED` | 200 | 上游未批准 |
| `E_CONFLICT` | 200 | 正文乐观锁冲突（附 `latest`） |
| `E_IO` | 200 | 文件读写失败 |
| `E_INTERNAL` | 200 | 未预期异常（附 `traceId`） |

> 注：connection 的 fetch 路由只有 GET/HEAD/POST，且 DSH 未提供统一错误传播；
> 业务错误一律返回 200 + `{ok:false}`，只有鉴权/路由级错误用非 200。

## 9. 批量原子提交与崩溃恢复（G1 终审 blocking #2 整改）

> 问题：只靠"单文件 tmp+rename + 内存回滚"无法保证 **canvas.json / content/*.md / events.jsonl 三者一致**。
> 本节的提交协议是 **`moxi-core` 写路径的唯一实现规范**，S2 起按此实现，S3 压测。

### 9.1 提交协议（Write-Ahead + 顺序提交）

一次 `canvas/apply`（或任一写工具）按以下顺序执行，**任一步失败即整体回滚**：

1. **校验**：全部 ops 在内存里应用到副本上；校验结构（DAG、状态机、字段）与乐观锁（`baseRev`）。
   - 失败 → 不落盘，返回 `E_TRANSITION` / `E_CONFLICT` / `E_BAD_REQUEST`。
2. **建 txn 目录 + 标记 + 旧值备份**（`history/txn/<txnId>/`）：
   ```
   history/txn/<txnId>/
   ├── txn.json          # 见下，原子写入
   └── backup/<safe>.md  # 本 txn 将要覆盖的每个 content 文件的**当前全文**（无损回滚的唯一依据）
   ```
   ```jsonc
   { "txnId": "txn_...", "baseRev": 12, "idempotencyKey": "sha1(...)",
     "ops": [...], "contentFiles": ["content/n_a.md"],
     "backups": [{ "file": "content/n_a.md", "backup": "backup/content__n_a.md",
                   "prevContentVersion": 4, "prevSha256": "..." }],
     "startedAt": "..." }
   ```
   - **硬规则**：备份必须在任何内容写入之前完成；`prevSha256` 必须与实际文件一致，否则中止（`E_IO`）。
   - 若同 `idempotencyKey` 已有**已完成**记录 → 直接返回上次结果（幂等），不重复执行。
3. **写正文文件**：逐个 `content/<id>.md` 原子替换（tmp+rename），并记录 `contentVersion`。
4. **写 canvas.json**：原子替换，`rev = baseRev + 1`。**这一步是提交点**。
5. **追加事件**：向 `history/events.jsonl` 追加本 txn 的全部事件（含 txnId / seq）。
6. **删 txn 标记**。

### 9.2 崩溃恢复（打开项目时执行）

| 崩溃位置 | 磁盘状态 | 恢复动作（**全部无损**） |
|---|---|---|
| 步骤 2 前 | 无变化 | 无事 |
| 步骤 2 备份未完成 | txn 目录不完整 | 删除整个 txn 目录（未写任何内容文件） |
| 步骤 2–3 之间 | 标记+备份完整，canvas.rev = baseRev | 逐个用 `backup/*` 覆盖回 `content/*`（并校验 `prevSha256`）；删 txn 目录 |
| 步骤 3–4 之间 | 有标记，canvas.rev = baseRev，部分正文已新 | 同上：全部用备份回滚（**不依赖 versions/ 快照**，因为快照可能落后于已提交修改）；删 txn 目录 |
| 步骤 4–5 之间 | canvas.rev = baseRev+1，事件缺失 | **前滚**：按标记补写事件；删 txn 目录 |
| 步骤 5–6 之间 | 全部写入，标记残留 | 检查事件里已有 txnId → 直接删 txn 目录 |

**无损保证**：回滚只用 `history/txn/<txnId>/backup/` 里本 txn 自己的旧值，不猜、不取"最近快照"。
备份与旧文件逐字节校验（`prevSha256`）；任何不一致 → 停在此处报 `E_IO` + 人工介入，**绝不静默继续**。

恢复实现要求：**幂等**、在项目级锁内执行、结果写一条 `system` 审计事件（`op: "txn.recover"`）。

### 9.3 局部写（非批次）

单节点正文保存（`node/save`）同样走 9.1 的 3→4→5→6（无图变更，`rev` 仍 +1，便于 UI 判断刷新）。

### 9.4 幂等键

- 默认由 `sha1(projectId + '|' + op + '|' + nodeId + '|' + contentHash)` 生成。
- 客户端可在 `canvas/apply` 显式传 `idempotencyKey`；工具调用自动生成。
- 幂等记录保留在 `history/txn/` 完成日志（保留最近 200 条，超出按时间清理）。

### 9.5 并发

- 同进程内：`Map<projectId, Promise>` 串行队列；跨进程（多 DSH 实例）：用 `project.lock` 文件（`O_EXCL` 创建，超时 5s 返回 `E_LOCKED`）。
- UI 侧：所有写操作带 `baseRev`，冲突时返回最新 `canvas` 让用户重试（不自动合并）。

## 10. 合规闸门策略（2026-11-06 补充，生成链路必须遵守）

| 风险级别 | 含义 | 是否阻塞导出 | 处理 |
|---|---|---|---|
| `redline` | 触碰平台硬红线（犯罪手法、未成年人受害、灵异恐怖具体画面等） | **阻塞**（delivery 不得 approved） | 生成后必须自动修复，5 轮内清不掉则该集合规 `rejected` |
| `high_risk` | 高风险但可人工判断（执法程序、暴力尺度、真实平台影射） | 不阻塞，记录并要求人工确认 | 写入合规节点 findings；delivery 可 approved，报告中标注"待人工签署" |
| `warning` | 提示性风险 | 不阻塞 | 记录 |

- `compliance.meta.highestRisk` 为三值枚举 + `none`；`meta.degraded=true` 表示模型评审不可解析（此时**禁止**自动批准）。
- 自动批准条件（`moxi-core` finalize）：`highestRisk !== 'redline' && degraded !== true`。
- 剧本生成提示词内置同一套红线（`lib/prompts.js` 第 6 条），先预防、后修复。
