## 优先级栈

| 层级 | 内容 | 可否被用户覆盖 |
|---|---|---|
| L0 | 平台合规、禁词 | **不可**，违反即拒收 |
| L1 | 用户实时指令 | —（本次最高） |
| L2 | 用户已定稿正史 / locked_facts / `no_change` | 可，但属**正史修订**，须显式确认 |
| L3 | 项目 config（字数、集数、赛道参数） | 可 |
| L4 | 规则默认值（`pipeline.toml` 与规则文件） | 可 |

## 三种作用域

用户一句话要求属于哪种作用域，**不允许猜**，判定不了就反问：

| scope | 含义 | 典型例子 |
|---|---|---|
| `episode` | 只影响当前这一集 | "这集写到 1200 字就收" |
| `project` | 持续生效，直到被解除 | "以后别再用会议室摔文件这套" |
| `canon_amend` | **正史修订**，影响后续所有集 | "主角其实有个双胞胎兄弟" |

**最危险的失败模式**：把 `project` / `canon_amend` 误当 `episode`——用户随口一句被当本集微调，结果后续集全部沿用；或反过来，全局禁令只管了一集。

## 落盘结构

维护 `<项目>/overrides/active.json`：

```json
{
  "version": 1,
  "items": [
    {
      "id": "ov_0007",
      "target": "word_count_max",
      "value": 1200,
      "scope": "episode",
      "episodes": [7],
      "ttl": "once",
      "source": "用户原话摘要",
      "created_at": ""
    }
  ]
}
```

`ttl` 取值：`once` / `until_episode N` / `forever`。

配套两个文件：

- `overrides/history.jsonl` —— 每次变更追加一行，可回溯
- `overrides/snapshots/ep{NN}.json` —— 每集生成时的生效快照，用于解释"这集为什么这么写"

## 冲突检测

| 用户要求 | 处理 |
|---|---|
| 字数 / 场数 / 时长 | 直接生效；低于平台下限时告警 |
| 结构（付费墙位置、钩子偏好、场次上限） | 生效；与已生成集冲突时列出受影响集号 |
| 内容禁令（禁用某梗/某组合） | 生效；并入 `used_beats` 禁用清单 |
| 内容新增（新设定） | 走 `canon_amend`，**必须确认** |
| 推翻已定稿事实 | 走 `canon_amend`，**必须确认**，列出受影响的所有集 |

触碰 `state_cards.no_change` 或 `canon_packet` 中已锁事实的要求，**一律报错并拒绝**，不接受"先写了再说"。

## 候选优先原则

借鉴 NarraLume：AI 产出永远先落为候选，经人接受后才是正史。

```
candidates/ep{NN}_v{N}.md   ← AI 产出落这里
episodes/ep{NN}.md          ← 用户 accept 后才是正史
```

这与项目 `AGENTS.md` 的硬规则一致：**用户定稿正史优先**——用户接受后的正文才是下一集生成的依据，不再进入阻断式质量门二次审查。质量门只检查新生成的内容是否承接了正史。

副作用是有价值的：`accept` / `reject` / 改稿幅度本身就是最强的用户偏好信号，比任何模型自评都可靠。

## 用户改稿的沉淀

用户实时修改是强信号，但不是规则真理（项目 `AGENTS.md` 科研硬规则）：

- 每次改稿 → 记入反馈池，标记 `source: user_edit`
- 不自动升级为质量门规则
- 累积到阈值（建议 10 个剧本项目）后生成审查包，由人工判断：哪些可升级为质量门、哪些只是本项目偏好、哪些属于污染规则
