# 评估场景

> **项目根（v2）**：规则包在 `<仓库>/rules/v2/`，脚本在 `<仓库>/scripts/`；项目数据由 moxi 工具管理（`~/Documents/Moxi/projects/<projectId>/`），**不要直接写项目数据文件**。


借鉴 Anthropic 的评估驱动原则：**先写评估，再写文档**。本项目最大的优势是拥有真实人评数据，可以直接做 ground-truth 回归，不必靠主观判断。

数据来源：`legacy-data/benchmark/human_scoring/`
- `calibration_anchors.md` —— 声明 27 高分 + 10 中分 + 49 低分，**正文实际收录 16 条**（6/4/6），按 16 条取用
- `calibration_coefficients.json` —— 75 个 (模型, 人评) 配对
- `episode_texts.json` —— 真实剧本文本
- `executor_negative_examples.md` —— 16 例真实失败案例
- `executor_high_score_openings.md` —— 7 集人评 ≥75 分开篇

## 场景 1：判定一致性（最关键）

**做法**：从 `episode_texts.json` 抽取已知人评结果的集，用 Skill 的质量门重新判定，比对人评 ground truth。

**通过标准**：

- 人评 A 类（benchmark 中位数 75-90）被 Skill 判 pass 的比例 ≥ 80%
- 人评 B/C 类（40-55 / 30-50）被 Skill 判 pass 的比例 ≤ 20%
- 若 B/C 类大量被判 pass → 质量门仍偏宽松，阈值需重标

**为什么关键**：`07_quality_check.md:71` 明确写了"模型历史均值 65 / 人评 49"——这正是质量门曾经失效的证据。没有 ground-truth 回归，无法知道新口径是否真的收紧了。

## 场景 2：漂移拦截

**做法**：构造一个含已知漂移的样本——角色名在第 8 集从"林若岚"变成"林若兰"，或让一个 `locked_facts` 中标记为已死的角色在第 12 集出场。

**通过标准**：

- 角色名漂移被规范名映射拦截，报硬失败
- "死人复活"被事实一致性检查拦截，且 `hard_reject_codes` 自动填 ③

**为什么关键**：这两类问题是 `hard_reject_codes` 里唯二**纯确定性可查**的（①重复、④动机崩、⑤无推进需要语义判断）。若脚本拦不住，说明确定性检查形同虚设。

## 场景 3：用户覆盖的作用域判定

**做法**：给出三条模糊的用户指令，验证 Agent 是否正确识别作用域、判定不了时是否反问：

1. "这集短一点" → 应为 `episode` scope
2. "以后别再用这套了" → 应为 `project` scope，需确认持续到何时
3. "其实她有个姐姐" → 必须识别为 `canon_amend`，反问确认，并列出受影响的集

**通过标准**：

- 第 3 条若被当作 `episode` 处理 → 不通过（这是最危险的失败模式）
- 触碰 `no_change` 的要求必须被拒绝，不能"先写了再说"

## 场景 4（补充）：伏笔积压

**做法**：构造一个前 10 集埋了 8 条伏笔、只回收 2 条的样本。

**通过标准**：台账报出积压告警，且与模型给出的高 `seed_payoff` 分形成冲突提示——模型分不可信时应当被标记，而不是照单全收。

## 运行方式

场景 1 可自动化：脚本读取 `episode_texts.json` + 人评结果，批量比对。

场景 2、4 可自动化（纯确定性检查）。

场景 3 需人工评判（考察 Agent 的交互行为）。

**每次修改质量门阈值或检查规则后，必须重跑场景 1 和 2。**
